## レビュー対象

以下のコマンドで変更差分を取得し、レビューしてください。

```bash
git diff
git diff --cached
```

未追跡の新規ファイルがある場合は、ファイル内容を直接読んでレビューしてください。

```bash
git status --short
```

## レビュー観点

1. **バグ・ロジックエラー** — 意図しない動作、エッジケースの見落とし、off-by-one エラー
2. **セキュリティ** — インジェクション、ハードコードされた秘密情報、安全でない入力処理
3. **可読性・保守性** — 不明瞭な命名、不必要な複雑さ、過剰な抽象化
4. **一貫性** — 既存コードベースのスタイル・パターンとの整合性
5. **コメント・docstring の置き場所** — 下記の方針からの逸脱

### コメント・docstring の置き場所

判断基準は CLAUDE.md「コメント・docstring の方針」を参照。

指摘してほしいもの:

- **コードの逐語訳になっているコメント**(「次に X する」)。コードを読めば分かることの重複
- **Why が書かれていない非自明な判断**。マジックナンバー・一見不要に見える分岐・
  あえて採らなかった実装があるのに理由が無いもの
- **docstring に契約が書かれていない**もの。前提条件・引数の破壊的更新の有無・
  送出する例外・呼び出し側の責務(例:「`asyncio.to_thread` で退避すること」)
- **実測データ・日付入りの調査結果がコードコメントに直接書かれている**もの。
  結論(Why)だけコードに残し、過程は外部ファイルへ移して参照させる
- **MEMO への参照がコードに書かれている**もの。MEMO は削除される前提のため、
  コードから恒常的に参照する情報は README に置く

逆に、**Why を説明しているコメントは冗長に見えても削除を促さない**こと。
陳腐化しにくく、消えると同じ判断が繰り返される。

## 言語固有のチェックポイント

変更されたファイルの言語に応じて、`languages/` ディレクトリ内の該当ファイルを参照してください:
- Python → `languages/python.md`
- TypeScript / React → `languages/typescript.md`

各ファイルには、言語特有のよくあるミスと参考資料がまとめられています。
**該当するチェックリストが無い言語は、上記「レビュー観点」の汎用観点だけでレビューしてください。**
(新しい言語を使い始めたら、その言語のチェックリストを `languages/` に追加する)

## 出力フォーマット

個人リポジトリのため、会話上で読みやすい簡潔な形式で出力してください。

- 指摘件数をまず冒頭に伝える
- 各指摘に「ファイル:行」と、重要度(高/中/低)を付ける
- 直接的な解決策のコードは示さず、アドバイスにとどめる
- 問題がなければ「問題ありませんでした。コミット可能です。」のみ出力

テンプレート:

```
指摘 N件

1. [重要度] ファイル:行
（問題の説明。アドバイス形式で。）

2. [重要度] ファイル:行
（問題の説明。アドバイス形式で。）
```
